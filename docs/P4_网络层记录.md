## 1. 为什么先做编解码，而不是直接挂 Steam P2P

游戏的联机栈是自研的（`W_NetworkManager` + `protocolChannel=1`），并且**加入大厅时校验游戏版本**。
直接在游戏通道里塞自定义消息，一旦格式不对，轻则断线、重则让主机/客户端进不了房间。

因此拆成三步，每步都可独立验证：

| 步骤 | 内容 | 状态 |
|---|---|---|
| ① 帧格式 + 编解码 | 自定义消息的线上格式、校验、边界处理 | ✅ 完成 |
| ② 传输抽象 | `IModTransport`，同一套代码跑 loopback / Steam P2P | ✅ 接口 + loopback 完成 |
| ③ Steam P2P 传输 | 在已建立的 P2P 会话上使用独立逻辑通道 | ⬜ 待做（需双端联调） |

## 2. 帧格式（`Net/ModCodec.cs`）

```
偏移  长度  内容
0     2     magic 'W' 'M'
2     1     版本 (1)
3     1     消息类型
4     1     ModId 长度（字节）
5     n     ModId（UTF-8）
..    4     payload 长度（uint32 LE）
..    n     payload
..    4     FNV-1a 校验和（uint32 LE，覆盖此前全部字节）
```

- 单帧上限 64 KB，`ModId` 上限 255 字节。
- 解码端对 magic / 版本 / 长度 / 截断 / 校验和 / 尾随字节逐项校验，任何异常都返回 `false` 并给出原因字符串，不抛异常。

## 3. 传输抽象

```csharp
public interface IModTransport {
    string Name { get; }
    bool Send(ModPacket packet);
    void Poll(Action<ModPacket> onPacket);   // 主线程轮询出队
}
```

`LoopbackTransport` 已实现（单机 Mod、回放测试、自测用）。
Steam P2P 传输留待下一轮：在 `W_NetworkManager` 已建立的 P2P 会话上使用独立逻辑通道（channel 5），
**不修改 `protocolChannel` 的任何字节**，避免影响游戏自身协议。

## 4. 自测结果

启动时自动运行（`NetSelfTest.Run`），覆盖：普通消息、空 payload、中文 ModId 与中文 payload、1 KB 大包、
篡改校验和、截断帧、错误 magic、队列排空。

```
[net] codec self-test: 16/16 passed
```

### 自测期间修掉的两个真实 bug

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 全部往返失败，16 项只有 3 项通过 | 编码缓冲区按 `6 + idLen + ...` 分配，多出 1 字节；解码按正确长度解析后判定"尾随字节" | 改为 `5 + idLen + 4 + payload + 4` |
| 2 | 仍失败，报 `checksum mismatch` | 解码端把**校验和字段本身**也计入了 FNV 计算范围 | 记录 `checksumPos`，只对校验和之前的字节求哈希 |
| 3 | 修完后仍报 `trailing bytes` | 尾随检查写成 `i + 4 != frame.Length`，但 `i` 已跨过校验和 | 改为 `i != frame.Length` |

> 这三个 bug 都是"差一个字节/差一个偏移"的经典问题——**先写自测再联调**的决定是对的，
> 否则它们会在真实联机里表现为随机断线，极难定位。

## 6. Steam P2P 传输（本轮新增，部分验证）

新增 `Net/SteamP2PTransport.cs` + `ModNet` 门面：懒初始化（Steam 就绪后自动接管）、
channel 5 收发、计数器与日志。

### 实测结果

| 观测 | 结果 | 说明 |
|---|---|---|
| Steam 就绪前调用 API | 抛 `Il2CppException: Steamworks is not initialized` | 已改为按状态变化只记一次日志（此前刷屏数千行） |
| 传输初始化 | ✅ `ready (channel 5), local id 76561199212697773` | Steam 起来后自动接管 |
| channel 5 启动时是否干净 | ✅ `idle at startup: True` | 未干扰游戏自有 1–4 通道 |
| 自发自收（自 SteamID 发包） | ⚠️ API 返回 `True`，首次实测确实读回一个 28 字节包 | 长度与探包完全一致 |
| 读回内容 | ❌ 首轮为全 0（`head=00-00-00-00…`） | Il2CppInterop 对 `byte[]` 出参不回写：原生层写进临时副本，托管数组仍是初值 |

### 已修

改用 `Il2CppStructArray<byte>` 作为接收缓冲（原生数组，写入可直接读回），并把初始化异常
改为按状态变化记录。修复后日志干净（75 行），本轮未再出现 `bad magic`。

**但单进程回环不能证明投递语义**：Steam 对"senda to self"的行为不稳定（本轮没再收到包），
真正的往返验证必须两个客户端。因此该传输标记为「已实现、单端可运行、待双端联调」。

## 7. 握手协议（已实现，待双端验证）

`Net/Handshake.cs`：

- 载荷 JSON：`{ "game": "2026.08.28", "mods": [{ "id", "version", "net" }] }`
- 消息类型：`Hello = 1`（发送自身清单）、`HelloAck = 2`（应答）
- 收到 `Hello` 自动回 `HelloAck`；收到 `HelloAck` 后比对并生成差异报告：
  `missing here: ...; extra here: ...; version: id 1.0≠1.2`
- **非阻断**：不匹配只写日志 + 面板提示，绝不阻止进房（游戏自身的版本校验仍然生效）
- 触发方式：每 300 帧（约 5 秒）检测 `W_NetworkManager.instance`：
  主机 → 遍历 `clients` 逐个发；客户端 → 发给 `getServerId()`。不在大厅时自动跳过。

面板新增 `net: <status>  recv N` 与 `mismatch: ...` 两行。

> 关于"Steam 报错"：那是 Steam 尚未初始化时调用 API 抛的异常，与网络加速器无关。
> 本轮开启加速器实测，日志与之前一致（`ready as 76561199212697773`、`channel 5 idle: True`、
> `recv 1` 收到自发探包），说明链路本身正常，**仍缺的是双端在线验证**。

## 8. 下一轮（P4 第二部分）计划

1. `SteamP2PTransport`：用 `SteamNetworking.SendP2PPacket/ReadP2PPacket` 在 channel 5 收发；
   需处理：会话未建立、发送失败、包大小限制、粘包/半包。
2. **先单机验证**：本机同时跑两个客户端不现实，改为在主机内做"自发自收"回环（send 到自己的 SteamID），
   确认通道独立、不影响 `protocolChannel`。
3. **再双端联调**：两台机器/两个账号，验证握手（Mod 清单交换）与消息投递。
4. 握手协议：`HELLO {mods[]}` → 对端比对 → 返回 `{accepted, missing}`；不匹配只提示，不阻断进房。
